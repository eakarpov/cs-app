# Морфемы в приложении: API и устаревающее представление карточки

Статус: **серверные методы реализованы и опубликованы 10 ноября 2026 года**.
Flutter-клиент работает с отдельной серверной публикацией морфем через API.
Локальная база в APK не поставляется; тестовые ответы используются только
в тестах. [Данные, проверки и ввод в действие](api-deployment.md).

С 11 ноября карточка поддерживает **schema=2**: [актуальный контракт](morpheme-graph-api.md).
Новый клиент запрашивает `morphemes/{id}?version={version}&schema=2`.
Описанные ниже плоские `structure[]` и `history[]`, а также запрос карточки без
schema, — **deprecated**. В ответе нового представления этих полей нет.
Получение морфем слова и постраничного списка слов остаются актуальными.
План удаления старого представления: `RETIRE-MORPHEME-SCHEMA1` в актуальном контракте.

## Методы

База: существующий `CS_API_BASE_URL` (`/api/v2/cs/`). Чтение публичное,
без мобильных секретов. Версия контракта — v1; `version` в ответах —
не версия контракта, а непрозрачный идентификатор неизменяемой публикации данных.
ID морфем передаются как один URL-encoded path segment.

| GET | Результат |
| --- | --- |
| `lexemes/{id}/morphemes` | Все опубликованные основные разборы словоформ данной словарной лексемы; основной словарной формы первым |
| `morphemes/{id}?version={version}` | Семантика, варианты, внутренняя структура, история и статистика морфемы |
| `morphemes/{id}/words?version={version}&limit=20&cursor={cursor}` | Уникальные словарные лексемы с этой морфемой, в стабильном порядке |

`id` слова — существующий ID из словарного API, НЕ исследовательский `L001`,
не ID исходной Chu-Rus-статьи. Ответы должны сохранять эту систему ID и для
переходов обратно к словам. Отсутствие разбора у известного слова — **200**
с `analyses: []`. В этом случае вкладка показывает: «Морфемный разбор этого слова пока не задан».
Клиент не подбирает разбор по похожему слову, не запускает эвристику и не делает
поисковых запросов для восстановления разбора. Неполный ответ без `analyses`
считается ошибкой API, а не отсутствием разбора. Неизвестный ID — 404. Неопубликованный сервис — 503.
В отсутствие маршрута старый сервер вернёт 404; клиент объясняет недоступность.
Сетевые ошибки и 429 имеют повтор; существующие правила CORS/OPTIONS и Retry-After
применяются также к этим маршрутам.

При неизвестной/снятой публикации — 409 `version_expired`: открыть разбор слова
заново. Сервер не подменяет запрошенную версию текущей. Каждый ответ содержит
`version`; клиент не смешивает версии карточки и списка слов.

## Разбор слова

Пример описывает форму и границы, а не новые редакторские решения:

```json
{
  "version": "morph-publication-sha256",
  "lexemeId": "existing-dictionary-id",
  "analyses": [{
    "id": "A-example",
    "form": "богъ",
    "status": "proposed",
    "note": "Рабочий письменный разбор.",
    "parts": [
      {"id": "p0", "morphemeId": "root:бог", "surface": "бог", "kind": "root", "gloss": "бог"},
      {"id": "p1", "morphemeId": "inflection:NOM_SG_HARD", "surface": "ъ", "kind": "inflection", "gloss": "Именительный падеж единственного числа"}
    ],
    "letters": [
      {"text": "б", "partIds": ["p0"], "colorKinds": ["root"], "note": ""},
      {"text": "о", "partIds": ["p0"], "colorKinds": ["root"], "note": ""},
      {"text": "г", "partIds": ["p0"], "colorKinds": ["root"], "note": ""},
      {"text": "ъ", "partIds": ["p1"], "colorKinds": ["inflection"], "note": ""}
    ]
  }]
}
```

Все поля в примере обязательны, кроме `morphemeId` (nullable для неустановленной
части). `parts[].id` уникален внутри разбора; `partIds` ссылаются только на него.
Порядок `parts` — порядок именованного списка. `surface` — морфемное написание,
может содержать редакторское `(ь)`; оно не генерируется по буквенным квадратам.
Пустое `surface` окончания отображается как ∅ в списке, без фиктивной буквы.

`letters[].text` — одна графема, включая её ударения и надстрочные знаки.
Конкатенация `text` в точности равна `form`. Координаты research-базы относятся
к Unicode code points нормализованной формы; перевод в графемы отображаемой
формы выполняет сервер через сохранённый alignment. UTF-16 индексы Flutter
не используются для восстановления границ. Титла автоматически не раскрываются.

`colorKinds` содержит один вид для обычной буквы и два различных вида для
штриховки. При слиянии двух однотипных морфем достаточно одного цвета;
семантическая подпись всё равно перечисляет обе. Например, я в ка-я-ти может
иметь `partIds: ["root", "theme"]`, `colorKinds: ["root", "thematic_vowel"]`.
В мощь общая щ может иметь цвета `root` и `derivational_suffix`; объяснение
и статус исторической гипотезы обязательны в `note` и карточке морфемы.
Историческое слияние не создаёт дополнительной письменной буквы. Если связанный
исторический формант отсутствует в письменном списке, API передаёт его цвет
через `colorKinds` и пояснение в `note`, без вымышленного письменного сегмента.

Виды и цвета:

| kind | Подпись | Цвет |
| --- | --- | --- |
| prefix | приставка | рыжий `#B94E0C` |
| root | корень | чёрный `#171717`, белый текст |
| interfix | соединительная гласная | тёмно-серый `#505050` |
| derivational_suffix | суффикс | синий `#2459B5` |
| formative_suffix | формообразующий суффикс | синий |
| stem_suffix | расширитель основы | зелёный `#247341` |
| thematic_vowel | тематическая гласная | зелёный |
| inflection | окончание | светло-серый `#E1E3E5`, тёмный текст |
| postfix | постфикс | синий |
| orthography / unresolved | орфографический элемент / неопределённая часть | нейтральный |

`thematic_vowel` — роль для представления, определяемая сервером по записи
морфемы, а не по букве. В исследовательской базе она может иметь kind stem_suffix.
Статусы: `approved`, `proposed`, `disputed`, `partial`. Старые и rejected-разборы
не попадают в основной ответ. Если есть несколько основных форм, пользователь
переключает их; альтернативы требуют отдельного будущего режима и не смешиваются
с текущей разметкой.

## Карточка морфемы — schema=1 (deprecated)

```json
{
  "version": "morph-publication-sha256",
  "id": "root:бог",
  "title": "бог / бож",
  "kind": "root",
  "status": "proposed",
  "gloss": "бог",
  "statistics": {"lexemes": 12, "forms": 13},
  "allomorphs": [{"id": "allomorph-id", "surface": "бог", "note": "Условия распределения.", "status": "proposed"}],
  "structure": [],
  "history": []
}
```

Числа выше иллюстративные. Статистика вычисляется сервером по той же выборке,
что `/words`: опубликованные основные разборы, только связанная словарная база,
слово учитывается один раз независимо от числа форм и повторений морфемы.
`forms` — количество различных форм. `allomorphs` содержит все опубликованные
варианты данной морфемы, в том числе ещё не встретившиеся в словах этой выборки.
Пустые списки означают отсутствие описания, а не доказанную простоту морфемы.

`structure[]`: `{title, note, status, morphemeId?}` — внутренняя структура
составной морфемы без дробления её письменного сегмента в разборе слова.
`history[]`: `{title, reconstruction, note, status, morphemeId?, protoId?,
bodySha256?, sources: [{title, locator}]}`. Поля со знаком `?` необязательны;
`protoId` — числовой публичный interlex ID, `bodySha256` — ожидаемая редакция
связанной статьи. Текст статьи по-прежнему загружается из interlex, не дублируется
как собственная этимология typikon. Источники и локаторы передаются для каждой
исторической связи; гипотезы не повышаются до approved при экспорте.

## Постраничный просмотр

```json
{
  "version": "morph-publication-sha256",
  "total": 12,
  "items": [{"id": "existing-dictionary-id", "name": "богъ", "gloss": "Бог"}],
  "nextCursor": null
}
```

`limit`: 1–100, по умолчанию 20; неверное значение — 400. `nextCursor: null`
означает последнюю страницу. Курсор непрозрачный, привязан к морфеме, версии,
лимиту и последней паре `(sortKey, lexemeId)`; неверный/чужой — 400.
Сортировка `(нормализованная лемма, словарный ID)` закреплена в публикации,
без зависимости от системной locale. `total` совпадает с `statistics.lexemes`.
Клиент хранит курсоры посещённых страниц, показывает номер и кнопки Назад/Далее.
Запрос следующей страницы не дописывает результаты предыдущей; повторы
и дубликаты между страницами недопустимы. Исторически родственные морфемы
не включаются в прямую статистику текущей морфемы автоматически.

## Серверная интеграция

Три Next.js route handlers реализованы рядом с `/api/v2/cs/lexemes`; данные
хранятся отдельной неизменяемой SQLite-публикацией. Каноническая коллекция
словарных статей не изменяется. Сборщик: `tool/morpheme_release/`.
Ниже — требования к дальнейшим публикациям.

1. Публиковать снимок исследовательской базы отдельным серверным артефактом.
   Создать таблицу `dictionary_morpheme_lexeme(dictionary_id, research_lexeme_id,
   witness_id, status, basis)`. Проверенные связи должны опираться на точную
   исходную статью и смысл/часть речи, не только на нормализованную строку.
   Неоднозначные соответствия остаются вне публичной выборки до проверки.
2. Сохранить allomorph, segment, etymology, sources и их статусы; при сборке
   сформировать проекцию `parts/letters` и фиксированные сортировочные ключи.
   Отдельно проверить fusion и нулевые окончания. В app не передавать локальные
   пути источников или служебные редакторские записи.
3. Индексы: mapping по dictionary_id; form по lexeme_id; analysis по form_id
   и is_primary; segment по allomorph_id; allomorph по morpheme_id.
   Для `/words` предварительно вычислить уникальные пары morpheme/dictionary_id,
   чтобы статистика и пагинация не выполняли полный проход базы на запрос.
4. Публикация атомарная; её hash становится version. Хранить прежнюю версию
   на время открытых клиентских сессий, ETag привязывать к URL и version.
   Неверный cursor/limit — 400, отсутствующая сущность — 404, снятая version —
   409, отсутствующий артефакт — 503. Формат ошибок существующего API сохранён.
5. До выкладки проверить: точные ID слов, отсутствие смешения омонимов,
   полное покрытие графем, допустимые partIds, неизменность базовых статей,
   дедупликацию статистики, все страницы без пропусков, версии, CORS и ошибки.

Привязка исследовательских лексем к словарным ID реализована с отдельным
отчётом неоднозначных/непривязанных записей. Клиентские проверки контракта: `flutter test test/morphemes_test.dart`.

## Уточнение связей форм — 11 ноября 2026

[Публикация 117 проверенных записей](linkage-117-deployment.md) использует адресацию
конкретных formId/analysisId. Разные формы исследовательской записи могут относиться
к разным словарным омонимам; варианты и причастия дополняют существующую карточку.
У новых элементов analyses доступны дополнительные поля formId, linkKind
(direct, variant, participle, homonyms), sourceGrammar. Клиент может игнорировать
их: человекочитаемая помета варианта/причастия передаётся также в note.
Порядок прежних разборов сохраняется, дополнительные формы следуют за ними.
